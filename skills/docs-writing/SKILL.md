# ドキュメントライティング

## 基本のドキュメント構成

```
README.md                   ← 利用者視点のプロダクト全体像、使い方、開発の初め方、システムの概観
docs/
├── architecture.md      ← システム構成（インフラ、開発環境、デプロイ）
├── <design>.md          ← 領域ごとの設計文書
├── adr/                 ← 設計判断の詳細記録
└── howto/               ← よくある開発タスクや運用タスクの手順
```

上記はデフォルト。プロジェクトごとの配置・規約を優先。

## 書き方の指針（共通）

- 「このドキュメントは誰が、どんなときに読むか」を最初に考える。
- 読者の知識コンテキストを意識する。
- 概要から詳細へ。
- 一時的なファイル（プランファイル等）を参照しない。
- コスパの高い（分量に対して読者への価値が高い）文章を書く。
  - 暗黙の前提、直感に反する仕様などを書く
  - コードの1箇所を見れば分かることは書かない
  - 内部挙動の細かい説明はコードコメントに書く

## 書き方の指針（ADR以外）

- コードの変化に常に追随して更新する。
- 変更の経緯はgitに委ねる。
  - 古くなった情報は削除。コメントアウトや取り消し線で削除を表現しない。
  - 過去の知識に依存する記述は禁止。最新版しか存在しないかのように書く。
    - 「AからBに変更した」ではなく、「Bだ」と書く
    - 「Xは必要なくなった」は、Xはもうないのだから、書かない
  - 歴史的事情による設計や実装がある場合は、その旨を端的に示す。


## <design>.md

一定の領域の設計に関する説明。

例:
- `s3-file-operations.md` S3への直アップロード、孤児ファイル掃除方法などについて
- `async-jobs.md` 非同期ジョブの実行環境、定期実行方法、テスト方法などについて
- `design-system.md` ビジュアルデザインの原則、配色、アイコンの使い方などについて

内容:
- 設計・モデル・フロー
- なぜその設計なのか
- 利用上の注意（直感に反する実情）
- 既知の制約や問題点


## ADR (Architecture Decision Record)

設計判断の記録。判断当時の状況や経緯、他の選択肢との
比較やトレードオフなど、その設計になった事情を記録する。

まず <design>.md を書き、そこに書ききれない事が多くある時はADRを作る。

一度作成したら基本的に更新しない。
ただし参照だけは切れないよう更新する。

ファイル名: `docs/adr/NNNN-<slug>.md`
番号は変えない。仮にADRを削除しても番号を再利用しない。

内容:
- コンテキスト: 何が問題で、どんな制約があったのか
- 決定: 何を選んだか
- 理由: なぜその選択が最善だったのか
- トレードオフ: この決定で受け入れた妥協点
- 採らなかった案との比較（なければ省略）

ルール:
- 短く書く。1ページ程度が目安
- 具体的なファイルパスなどは陳腐化するので書かない


## How-To

開発時のよくあるタスクや運用タスクの手順を書いたもの。

例:
- `docs/howto/add-model-field.md` モデルに新フィールドを追加する際に決まって行う設定や変更箇所について
- `docs/howto/blue-green-deployment.md` Blue-Greenデプロイの手順
- `docs/howto/update-fixtures.md` 正解出力ファイルの再出力・差分検証手順
