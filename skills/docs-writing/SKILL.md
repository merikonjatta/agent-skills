# ドキュメントライティング

## 活性化の条件

以下の状況でこのスキルを参照する。

- `docs/` 配下のファイルを作成・編集・レビューするとき
- ADR (Architecture Decision Record) を起票するとき
- 設計判断や構成の「なぜ」を記録する必要があるとき

## ドキュメント構成

```
docs/
├── concept.md           ← ユーザー視点のプロダクト全体像（何を解決するか、誰のためか）
├── architecture.md      ← 開発者視点のシステム構成（インフラ、開発環境）
├── <feature>.md         ← 機能ドメインごとのモデル・フロー・設計判断
├── adr/                 ← 設計判断の詳細記録
└── howtos/              ← よくある開発や運用タスクの手順
```

## 書き方の指針

- 読者を意識する。「このドキュメントは誰が、どんなときに読むか」を最初に考える。
- 概要から詳細へ。
- 設計の「なぜ」を重視。
- 具体的に書く。「パフォーマンスのため」ではなく「LibreOfficeが最大2GBのメモリを消費し、Webリクエストのレスポンスが劣化するため」。
- 変更の経緯はgitに委ねる：
  - 古くなった情報は削除。コメントアウトや取り消し線で削除を表現しない。
  - 過去の知識に依存する記述は禁止。最新版しか存在しないかのように書く。
  - 歴史的事情による設計や実装がある場合は、その旨を端的に明示する。

## ADR テンプレート

ファイル名: `docs/adr/NNNN-<slug>.md`

番号は既存の最大番号 + 1 を採番する。初回は `0001` から開始。

```markdown
# ADR-NNNN: タイトル

## ステータス

提案中 / 採用済み / 廃止（YYYY-MM-DD）

## コンテキスト

何が問題で、どんな制約があったのか。

## 決定

何を選んだか。

## 理由

なぜその選択が最善だったのか。

## トレードオフ

この決定で受け入れた妥協点。
```
